# 평가 하니스 (evals)

JisangFolio 챗봇과 데이터분석 라우터의 출력 품질을 **재현 가능하게** 검증하는 회귀 테스트.
프롬프트나 모델을 바꾸기 전후로 돌려 품질이 깨지지 않았는지 정량 확인한다 (실시간 가드가 아니라 오프라인 평가).

## 실행

```bash
python evals/run_evals.py            # 전체 실행 (20건 · 약 71k = 일일한도의 35%)
python evals/run_evals.py --dry-run  # 비용 추정만 (API 호출 없음)
python evals/run_evals.py --quick    # 카테고리별 1건씩 (반복 수정 중 스모크)
python evals/run_evals.py --no-judge # 결정적 채점만
python evals/run_evals.py --resume   # 중단된 실행 이어하기 (끝난 케이스는 호출 없이 재사용)
```

### 골든셋을 왜 48 → 20건으로 줄였나

**배포된 앱과 이 하니스가 같은 Groq 키·같은 일일 예산(20만 토큰)을 쓴다.** 48건짜리 전체
실행은 약 169k(84%)여서, 인자 없이 한 번 돌리는 것만으로 그날 사이트 방문자가 429를 봤다.
채용담당자에게 보여주려고 만든 포트폴리오에서 이건 평가가 실패하는 것보다 나쁘다.

처음엔 기본값만 작은 티어로 바꿔서 피했는데, 그러면 **나머지 28건은 영원히 안 도는 장식**이
된다. 못 돌리는 케이스는 없는 케이스다. 그래서 세트 자체를 줄였다.

| | 케이스 | 추정 | 일일한도 대비 | 방문자 몫 |
|---|---|---|---|---|
| 전(48건) | 19 챗봇 · 20 라우터 · 9 RAG | ~169k | 84% | 챗 5턴 |
| **지금(20건)** | 9 · 8 · 3 | **~71k** | **35%** | 챗 21턴 |

**남긴 기준 = 깨지면 사실이 틀리는 것, 그리고 모델을 불러야만 알 수 있는 것.**

- 챗봇 9건: 메모리에 박힌 가드레일을 그대로 어서션하는 3건(Kubeflow 미사용 · Butterworth는
  노이즈 필터링이지 이상치 제거가 아님 · PyTorch 모델은 부경대 제공)과 대표 수치 1건,
  영어 경로 1건, 그리고 주제이탈·인젝션을 **한/영 각각** 1건씩. 페르소나가 인젝션에
  버티는지는 문자열 검사로 대체할 수 없어서 이쪽은 언어별로 남긴다.
- 라우터 8건: 클래스당 4건, 질문 형태가 겹치지 않게(집계·랭킹·시각화·메타 / 정체·도메인
  의미·해석·요약). 케이스당 800토큰이라 커버리지가 싸다.
- RAG 3건: 한국어 검색(최난이도) · 영어 벤더 문서 · 코퍼스 밖 거절.

**뺀 28건은 지운 게 아니라 `evals/archive/` 로 옮겼다** — 대부분 같은 성격을 반복 검증하던
케이스이고(예: 인젝션 4건 → 공격 유형×언어 2건), `factual` 다수는 `tests/test_resume_facts.py`
가 **토큰 0**으로 이미 드리프트를 잡는다(골든셋 근거 문구가 이력서에 살아있는지 검사).
유료 호출이 추가로 답하는 질문은 "봇이 그걸 실제로 꺼내오는가" 하나뿐이다.

실행 전에는 항상 예상 비용 · **오늘 이미 쓴 양** · 방문자에게 남는 몫을 출력하고,
남은 예산보다 크거나 하루치의 40%를 넘으면 `--force` 없이는 시작하지 않는다.
`tests/test_eval_budget.py`가 예산선과 커버리지(카테고리·언어·archive 보존)를 고정한다.

무료 티어는 **분당 토큰(TPM)** 상한도 낮아 긴 실행이 429로 끊길 수 있다. 그래서
① 429는 서버가 알려준 대기시간만큼 쉬고 재시도하고, ② 한 케이스가 실패해도 나머지는 계속
돌며, ③ 섹션이 죽어도 이미 채점된 결과로 리포트를 쓰고, ④ `--resume`이 남은 케이스만
이어서 돌린다. 캐시는 **프롬프트·모델·이력서가 바뀌면 자동 폐기**된다 — 회귀 게이트가
낡은 PASS를 재활용하면 거짓 안심이 되기 때문.

`.streamlit/secrets.toml` 의 `groq_api_key`, `resume_text` 를 사용한다.

## 무엇을 검사하나

| 대상 | 골든셋 | 채점 |
|---|---|---|
| 챗봇 | `golden_chat.jsonl` (9) | 결정적 규칙(사실 키워드·금지어·형식) + LLM judge |
| 라우터 | `golden_router.jsonl` (8) | PANDAS/RAG 분류 정확도(%) |
| Agentic RAG | `golden_rag.jsonl` (3) | 결정적 키워드(포함·금지) + 검색 vendor 히트 + 근거 자기점검(grounded) |

합계 **20건**(+ `archive/` 28건은 보존만). 아래 §회귀 사례의 `10/16 → 15/16` 은 **당시
16건이던 챗봇 셋**에서 잰 값이라 지금 셋과 크기가 다르다 — 지난 수치를 현재 셋 크기로
소급해 쓰지 않는다. `tests/test_goldenset_counts.py` 가 이 표와 실제 파일 줄 수를 대조한다.

- **결정적 채점(백본)**: 사실 키워드 포함 / 금지어 미포함 / 형식 규칙(한자·가나·볼드).
  금지어 검사는 사실 정확성 제약을 그대로 어서션으로 박는다 — 예: 사용한 적 없는 도구를
  썼다고 주장하지 않는가, 출처를 정확히 밝히는가.
- **LLM judge(보조)**: 자기채점 편향을 피하려 챗봇과 **다른 모델**로 grounding·페르소나·거절을 판정.
  유도질문/주제이탈/인젝션처럼 substring으로 판별 불가한 케이스의 게이트.
  **판정을 바꿀 수 있는 카테고리(`factual-guard`·`offtopic`·`injection`)에만 호출한다** —
  `factual`은 결정적 채점이 게이트라 judge를 불러도 결과에 반영되지 않았고, 당시 골든셋
  16건 중 11건이 그런 낭비 호출이었다(정보 손실 없이 judge 호출 69% 절감).
- **앱과 동일 경로(모델 계층)**: 프롬프트(`prompts.py`)와 출력 후처리(`clean_response`)를 앱 페이지와
  공유해 '사용자가 실제로 보는 출력'을 검증한다. RAG는 앱 페이지와 같은 `agentic_answer`
  (검색→관련성평가→쿼리재작성→생성→근거 자기점검)를 그대로 호출한다.
  단, **가드레일 레이어(`guardrails.py`)는 이 경로에 없다** — 앱은 guard→LLM, 평가는 LLM 직행이다.
  즉 골든셋의 인젝션 케이스는 '가드가 막았는가'가 아니라 '가드를 통과했을 때 페르소나가
  버티는가'를 재는 것이고, 가드 자체는 `tests/test_guardrails.py`가 검증한다(한/영 대칭).

## 이 하니스가 잡아낸 회귀 (예시)

도입 직후 첫 실행에서 챗봇 사실 정확성 통과율이 낮게 나왔고, 원인은 주입되던 이력서 텍스트가
**낡은 사본으로 드리프트**한 것이었다(정정된 마스터본과 불일치 + 정량 성과 누락). 소스를 단일
기준으로 정리하자 챗봇 골든셋 통과율이 **10/16 → 15/16** 으로 회복됐다. 단일 진실 소스 부재가
어떻게 출력 품질로 새는지를 보여준 사례.

> ⚠️ **재측정 대기**: 이 수치는 하니스 자체의 버그를 고치기 **전**에 잰 값이다.
> 골든셋은 `"lang": "ko"`, 앱은 `"한국어"` 를 쓰는데 둘이 `lang == "한국어"` 비교에서
> 만나면서 챗봇 19건 중 15건이 **영어 프롬프트로 실행된 뒤 한국어 키워드로 채점**되고
> 있었다(`normalize_lang` 으로 수정). 즉 10/16 → 15/16 은 지금의 하니스를 설명하지
> 않는다. 전체 48건 재실행은 약 206k 토큰으로 무료 일일한도(20만)를 넘고, **배포된 앱이
> 같은 키를 쓰므로** 전체 실행은 방문자에게 429를 안긴다 → `core: true` 8건(`--quick`,
> 약 42k)으로 나눠 재측정하고, 실제로 측정된 값만 채운다(추정치로 채우지 않는다).
> 현재까지 채점된 내용은 `runs/` 의 최신 기록이 기준이다.

**이 수치를 읽는 법**: n=16짜리 단일 골든셋의 before/after이지 벤치마크가 아니다. 같은 16문항
쌍대 비교라 McNemar가 맞는 검정인데 p≈0.06으로 α=0.05에 못 미치고, Wilson 신뢰구간도 겹친다.
"통과율이 올랐다"가 아니라 **"드리프트를 하니스가 잡아냈고 고친 뒤 통과 케이스가 늘었다"** 로
말하는 게 정확하다.

## 한계

- 결정적 키워드 채점은 표면 매칭이라 '키워드는 있으나 맥락이 틀린' 거짓 통과 가능 → judge가 보조.
- LLM judge는 비결정적 → 하드 게이트는 결정적 채점에 둠.
- 라우터 정확도는 표본이 작고 일부 라벨 경계가 주관적 → 절대 수치보다 변경 전후 비교에 의미.
- 챗봇 평가는 단발(single-turn) 경로이며 멀티턴 회귀는 범위 밖.
- RAG 근거 자기점검(grounded)도 LLM 판정이라 비결정적이고 표본 n이 작다 → 회귀 비교용 지표.

## 사용 패턴 (회귀 게이트)

프롬프트나 모델을 바꾸기 **전** 돌려 통과율을 기록하고, 바꾼 **후** 다시 돌려 before/after를 비교한다.
'프롬프트 한 줄 수정이 사실 정확성·형식 규칙·라우팅을 깨뜨리지 않았는지'를 정량 확인하는 게 목적이다.
### 산출물 두 가지

- **`evals/report.md`** — **가장 최근의 전체 실행** 스냅샷. 매번 통째로 덮어쓰는 생성물이니
  손으로 고치지 말 것. **부분 실행(`--rag-only`·`--quick`·한도 중단)은 이 파일을 건드리지 않는다** —
  예전엔 부분 실행 한 번에 직전 전체 실행의 챗봇·라우터 섹션이 통째로 날아갔다.
- **`evals/runs/<타임스탬프>_<핑거프린트>.json`** — 실행 **이력**. 부분 실행도 여기엔 남되
  `partial: true`로 표시된다. 각 레코드에 섹션별 통과 수·카테고리 분해·모델 구성·그때의
  report.md 본문이 함께 들어 있어, "언제 어떤 구성에서 몇 점이었나"를 나중에 추적할 수 있다.

핑거프린트는 모델·프롬프트·이력서를 해시한 값이라, **셋 중 하나라도 바뀌면 값이 달라진다** →
서로 다른 핑거프린트끼리는 통과율을 직접 비교하면 안 된다.
