# On-prem MLOps Pipeline (KETI) — Architecture & Design Rationale

단일 GPU 서버 위에서 딥러닝 모델을 서빙하는 온프레미스 자체호스팅(폐쇄망 대응 설계) MLOps 파이프라인의 **설계 문서**다.
필자가 KETI에서 주도적으로 설계·구축하고 운영했으며, 범위는 **모델 서빙과 그 주변 MLOps 인프라**
— ONNX export → Triton 서빙 → MLflow 레지스트리 → Gitea Actions CI → Prometheus/Grafana 관측 — 이다.
모델 아키텍처 설계는 범위 밖이다(학습 모델은 외부에서 수령).

**스택:** NVIDIA Triton (추론 서빙) · MLflow (실험관리 + 모델 레지스트리) · Gitea + Gitea Actions
(자체호스팅 Git + CI) · Prometheus + Grafana (메트릭·관측) · Docker Compose (오케스트레이션) ·
ONNX / ONNX Runtime (모델 교환 포맷).

---

## 1. 범위와 경계

### 1.1 이 파이프라인이 푸는 문제

여러 출처에서 만들어진 **이종(heterogeneous) 딥러닝 모델을 한 대의 GPU 서버에서 통일된 방식으로
서빙하고, 그 라이프사이클을 추적 가능하게 관리**하는 것이 목표다. 구체적으로는 협업 대학(부경대)이
제공한 도시냉각 3D U-Net 대리모델과, 외부 협업팀에서 수령한 물리기반 신경망(PINN) 계열 모델들을
같은 추론 서버·같은 레지스트리·같은 배포 워크플로 위에 올렸다.

### 1.2 의도적으로 좁힌 책임 경계

모델은 두 경로로 들어온다. 협업 대학이 제공한 3D U-Net은 학습 코드와 데이터를 받아 **이 서버에서
학습**하고, 외부 개발팀의 PINN은 **ONNX 파일로 전달**된다(Git push가 아니라 파일 전달).

처음(2026-06)에는 자체 학습 사이클이 CI 밖에 있었기 때문에 CI의 책임 범위를 **"받아서 서빙까지
(receive-and-serve)"** — 수령 → 검증 → Triton 배포 → 레지스트리 거버넌스 갱신 — 로 명시적으로 좁혔다.
2026-08-18부터 학습 사이클이 CI 안으로 들어와, 내부 학습 모델에 대해서는 **학습 → 판정 → 변환 →
배포**까지 CI가 책임진다(§5.1). 외부 수령 모델에는 receive-and-serve 경계가 그대로 적용된다.
이건 "CI/CD를 다 못 했다"가 아니라 **"모델의 출처에 따라 CI가 책임져야 할 범위를 정의했다"** 에 가깝다.
학습 데이터가 갱신되는 경로는 아직 없다 — 그래서 자동 재학습이 도는 것과 모델이 개선되는 것은
별개라는 점을 §12에서 분명히 한다.

### 1.3 이 문서가 다루지 않는 것

호스트·포트·계정·권한 정책 같은 운영 환경 세부, 조직 내부 의사결정 기록, 시점에 따라 변하는
라이브 상태 스냅샷은 다루지 않는다. 이 문서에 남긴 것은 **시간이 지나도 유효한 설계 판단과
그 근거**다.

## 2. 아키텍처 개요

### 2.1 컴포넌트 구성

| 레이어 | 도구 | 역할 |
|---|---|---|
| 추론 서빙 | NVIDIA Triton Inference Server | 멀티 프레임워크 모델 서빙, GPU 메트릭 노출 |
| 실험관리·레지스트리 | MLflow (2.18) | 학습 메트릭 추적, 모델 버전·태그 거버넌스, 아티팩트 프록시 |
| 소스·CI | Gitea + Gitea Actions | 자체호스팅 Git, 워크플로 실행 |
| 관측 | Prometheus + Grafana | 메트릭 수집·시각화 |
| 학습 환경 | PyTorch 컨테이너 | GPU 학습 실행 |
| 드리프트 | Evidently (PoC) | 입력 분포 변화 관측 |
| 운영 UI | Streamlit 포털 | 업로드·리스트·모니터링·거버넌스·추론 테스트를 한 화면에 통합 |

모든 컴포넌트는 Docker Compose로 단일 서버에 올라가며, 외부 SaaS 의존이 없다.

### 2.2 모델이 흐르는 경로

```
외부 수령 ONNX
   → CI: 구조 검증 · 동적 배치 검증 · 더미 추론 검증
   → model repository 배치
   → Triton load API 호출 → READY 폴링
   → MLflow: 이전 버전 retire + 신규 버전 등록 + deployed 태깅
   → Prometheus가 Triton 메트릭 수집 → Grafana 대시보드
```

핵심은 **파일 복사가 곧 배포가 아니라는 점**이다(§3.1). 배포는 명시적 API 호출과 준비 상태 확인까지
끝나야 완료로 친다.

## 3. 추론 서빙 — Triton

### 3.1 EXPLICIT model-control-mode를 택한 이유

Triton은 모델 로딩 방식을 POLL과 EXPLICIT 중에 고를 수 있다. POLL은 모델 저장소의 파일 변화를
감지해 자동으로 로드하고, EXPLICIT은 **API로 명시 호출해야만** 모델이 올라간다
(`POST /v2/repository/models/<name>/load`).

EXPLICIT을 택했다. 이유는 거버넌스다 — POLL이면 "누가 언제 무엇을 올렸는지"가 파일시스템 이벤트에
묻히지만, EXPLICIT이면 **모든 로드가 명시적 호출로 기록**된다. 대신 대가가 있다: CI에서 ONNX를
자동 배포할 때 **파일 복사만으로는 모델이 안 붙는다.** 그래서 배포 워크플로의 마지막 단계가 반드시
`load` API 호출 + READY 폴링으로 설계되어 있다(§5.3). 서버 동작 방식의 차이가 CI 설계를 규정한 사례다.

부수 인자들도 같은 방향이다. `--exit-on-error=false`로 한 모델의 로드 실패가 서버 전체를 죽이지
않게 했고(다중 모델 서빙의 가용성 보호), `--strict-model-config=false`로 ONNX 메타데이터에서 일부
설정을 자동 추론하게 했다.

### 3.2 모델 저장소는 읽기 전용으로 마운트

서빙 컨테이너에 모델 저장소를 **읽기 전용(ro)** 으로 붙였다. 서빙 프로세스가 모델 바이너리를
변조할 수 없게 만들고, 배포는 오직 "저장소 파일 교체 + load API"라는 통제된 경로로만 일어나게 하기
위해서다. 최소 권한 원칙을 마운트 수준에서 적용한 것.

### 3.3 이종 모델의 텐서 contract — U-Net과 PINN은 다르게 설계해야 한다

이 파이프라인의 실질적 난점은 "여러 모델을 올린다"가 아니라 **"입출력 형태가 근본적으로 다른 모델들을
같은 서버에 올린다"** 였다. 모델별 `config.pbtxt`를 직접 설계했다.

**도시냉각 3D U-Net (voxel 회귀)**

- 입력: 좌표 격자 `[4, 128, 128, 20]`(4채널 3D 격자) + 운전조건 스칼라 `[5]`
- 출력: 냉각효과 격자 `[1, 128, 128, 20]`
- `max_batch_size: 4`, dynamic batching 사용

**PINN 계열 (좌표 → 물리량 회귀)**

- 입력: `[-1, 3]` — 임의 개수 N개의 (x, y, z) 좌표점
- 출력: 유동 모델은 `[-1, 4]`(u, v, w, p), 열 모델은 `[-1, 1]`(무차원 온도)
- `max_batch_size: 0` + 첫 차원 `-1`, dynamic batching 미사용

PINN은 **한 점씩 forward가 가능**(autoregressive 아님)하기 때문에 "임의 N개 점을 한 번에 평가"가
자연스러운 추론 패턴이다. 이건 이미지 배치와 의미가 다르다 — 그래서 일반 배치 개념(`max_batch_size`)을
끄고 첫 차원을 동적으로 열었다. **모델의 수학적 성질이 서빙 설정을 결정한 사례**다.

PINN이 학습한 물리는 각각 Navier-Stokes(운동량·연속 방정식), 유체 내 열전달, 고체 내 열전도다.

### 3.4 동적 배치 — 적용했으나 튜닝하지 않았다

U-Net에만 dynamic batching을 켰다(`preferred_batch_size: [1, 2]`, 큐 지연 상한 100µs).
다만 **이 수치는 부하 측정으로 튜닝한 값이 아니라 안전값**이다. 배칭을 성과로 말할 수 있는 범위는
"적용 경험"까지고, "최적화했다"는 아니다.

### 3.5 관측을 전제로 한 서빙 설정

Triton의 메트릭 노출을 켜서 Prometheus가 수집할 수 있게 했다. 노출되는 것 중 설계상 의미 있는 것은
추론 지연을 **단계별로 분해한 메트릭**이다 — 큐 대기 시간, 입력 처리, 실제 연산, 출력 처리가 각각
분리돼 있어 "느리다"를 "어디가 느리다"로 좁힐 수 있다. 여기에 GPU 사용률·메모리·전력이 더해진다.

## 4. 실험관리·모델 레지스트리 — MLflow

### 4.1 최신이 아니라 안정 버전을 골랐다

MLflow 3.x에는 same-origin 정책 미들웨어 버그가 있어 **UI에서 모델·실행 삭제가 동작하지 않았다.**
재현·진단한 뒤 2.18로 내려서 해결했다. "최신 버전이 항상 정답은 아니다"를 실제 회귀로 확인한 사례.

### 4.2 아티팩트 프록시 모드 — 폐쇄망 친화적 선택

MLflow를 `--serve-artifacts` 모드로 띄웠다. 클라이언트가 오브젝트 스토리지에 직접 PUT 하지 않고
**MLflow 서버를 프록시로 경유**하는 방식이라, 클라이언트 측에 스토리지 자격증명을 뿌릴 필요가 없다.
폐쇄망 제약과 (§10.2의) 오브젝트 스토리지 제거 결정을 동시에 만족하는 구성이었다.

백엔드 스토어는 SQLite다. **단일 운영자·소규모 규모임을 정확히 표현해야 한다** — 프로덕션급 트래킹
서버가 아니다.

### 4.3 표준 스테이지 대신 태그 기반 거버넌스

MLflow의 표준 스테이지(Staging/Production)를 **쓰지 않았다.** 모든 버전이 `current_stage=None`이고,
라이프사이클은 태그로 표현한다.

이유는 표현력이다. 표준 스테이지는 사실상 3단계뿐이라, **외부에서 수령한 모델**의 상태
(received → validated → deployed → retired)나 모델 출처·도메인·물리 특성 같은 메타데이터를 담을 수
없다. 태그 스키마를 직접 설계해 다음을 표현했다:

- 라이프사이클: `status`(4단계 단방향), `received_at` / `validated_at` / `deployed_at` / `retired_at`
- 출처: `source`, `contact`, `source_type`
- 모델 성격: `model_type`, `domain`, `physics`, `framework`, `opset`
- 서빙 연동: `triton_loaded`, `manifest_validation_status`

### 4.4 거버넌스 스키마 v2 — 무엇을 넣고 무엇을 거절했나

v1(단방향 status 태그) 운영 뒤 피드백을 받아 v2로 격상했다. 결정과 그 근거:

| 안건 | 결정 | 근거 |
|---|---|---|
| Timestamp 포맷 | ISO 8601로 통일 | date-only는 같은 날 두 번 배포하면 구분 불가, 정렬도 안 됨 |
| Status enum | 4단계 단방향 유지 (`staging` 추가 거부) | 의미가 모호해지고 v1 호환이 깨짐 |
| 필드 구조 | 고정 필수 + 자유 tag **이중구조** | 필수만 강제하면 모델별 특이 메타를 못 담고, 자유만 두면 통일이 안 됨 — 약한 통일 채택 |
| Approval 단계 | 미도입 | 이 규모에 과대. 외부 감사 의무 없음 |
| 추론 히스토리 | 보류 (YAGNI) | Triton 메트릭 카운터로 충족. 추론 1건씩 추적은 트래픽이 늘면 그때 |

v1을 폐기한 게 아니라 **확장**했다는 점이 중요하다 — 단방향 status와 태그 기반 운영은 그대로 두고
필수 필드를 얹었다.

### 4.5 한때의 갭 — 레지스트리 상태 ≠ 실제 서빙 바이너리, 그리고 어떻게 닫았나

2026년 6~8월에는 정직하게 남겨둘 갭이 하나 있었다. 레지스트리에는 재학습된 최신 버전이 `deployed`로
태깅돼 있었지만, **Triton이 실제로 서빙하는 ONNX는 그보다 이전 빌드**였다. 원인은 성능이 아니라
구조였다 — 배포 워크플로의 입력이 **저장소에 커밋된 ONNX 파일 경로**였고, 그 경로가 초기 커밋의
blob을 가리키고 있어 워크플로를 다시 돌려도 같은 바이너리가 나갔다. 즉 "레지스트리의 deployed 태그
= 실서빙 바이너리"라는 가정은 저절로 성립하지 않는다.

2026-08-19에 배포 정본을 **커밋 파일에서 레지스트리로 옮겼다.** 지금은 체크포인트를 MLflow에서 받아
ONNX로 변환하고, 만든 ONNX를 **같은 모델 버전에 첨부**한 뒤, 배포 워크플로가 레지스트리에서 회수해
**SHA-256을 대조**하고 Triton에 싣는다. 버전 태그의 `onnx_sha256`과 서빙 파일의 실측 해시가 일치하는지가
확인 절차다(2026-09-15 기준 배포본 v12에서 일치 확인).

이 이력을 지우지 않고 남기는 이유는, "발견 → 정본 이전 → 해시 대조로 재발 차단"이 이 파이프라인에서
가장 설득력 있는 서사이기 때문이다.

또한 일부 수령 모델은 검증 미완(`demo_only`) 상태로 태깅된 채 로드돼 있다. 따라서 "N개 모델 서빙 중"은
**'로드·READY' 사실**이지 '전부 운영 검증 완료'가 아니다. 이 불일치는 이제 운영 콘솔의 점검 항목으로
매일 드러난다(§9).

## 5. CI — Gitea Actions

### 5.1 워크플로 구성 — 3종에서 8종으로

처음(2026-06)에는 워크플로가 3종이었다.

| 워크플로 | 트리거 | 역할 |
|---|---|---|
| 문법 검사 | push / PR (자동) | 치명 오류 lint + 핵심 스크립트 `py_compile` |
| ONNX 검증 | 수동 dispatch | ONNX 파일 3단계 검증 |
| 배포 | 수동 dispatch | 검증 → 배치 → Triton load → READY 폴링 → 거버넌스 갱신 |

이 시점엔 자동 재학습·재배포 트리거가 없었고 배포는 사람이 트리거했다. 2026-08-18부터 학습 사이클이
CI 안으로 들어오면서 8종이 됐다.

| 워크플로 | 하는 일 | 자동 발화 |
|---|---|---|
| 학습 | 데이터 검증(정상 비율 98% 미만이면 시작하지 않음) → 학습 컨테이너에 `docker exec` 위임 → 레지스트리 버전 등록 | 주 1회 스케줄 |
| 판정 | 등록 버전 성능 판정 → `candidate` / `rejected` 태그 | 학습 뒤 스케줄 + 콘솔 상시 |
| 변환·첨부 | 체크포인트 회수 → ONNX 변환·검증 → **같은 버전에 첨부** | 판정 통과에 이어서 |
| 배포 | 레지스트리에서 산출물 회수 → **체크섬 대조** → Triton load → READY 폴링 | 변환에 이어서 |
| 알림 점검 | 콘솔 점검 결과를 Git 이슈로 발행·회수 | 평일 2회 |
| 문법 검사 · ONNX 검증 · 포털 재기동 | 보조 워크플로 3종 | push · 수동 |

**설계 판단 4가지.**

1. **학습을 잡 컨테이너가 아니라 상주 학습 컨테이너에 위임했다.** 잡 컨테이너를 GPU 이미지로 띄우는
   1차 시도는 러너의 볼륨 허용 목록에 막혔고 런타임 이미지에 `git`이 없어 checkout도 실패했다.
   러너가 잡 컨테이너에 docker 소켓을 넣어 주므로, 이미 데이터·GPU가 물려 있는 컨테이너에
   `docker exec`로 위임하면 러너 설정을 바꾸지 않고 동작한다.
2. **배포 정본을 커밋 파일에서 레지스트리로 옮겼다**(§4.5).
3. **판정 기준을 코드에서 빼 과제 매니페스트로 옮겼다.** 판정 스크립트에는 숫자가 없고 과제 매니페스트를
   읽는다 — 절대 기준(test MAE / R²)과 **현 배포본 대비 허용 악화폭**(MAE 비율·R² 절대값)을 함께 본다.
   판정이 실제로 미달 버전 2건을 기각해 배포를 막았다.
4. **알림을 외부로 보내지 않고 Git 이슈로 만들었다**(§6.1).

**실행기 제약이 설계를 바꾼 사례.** 실행기의 잡 수명이 30분인데 학습은 32~66분 걸린다. 처음엔
"학습 2시간 뒤 판정"을 스케줄로 걸었으나, 이는 시간으로 짐작하는 방식이라 학습이 더 걸리면 빈손으로
돌았고 한 번은 실행기와 함께 죽어 한 주가 날아갔다. 지금은 운영 콘솔이 **판정 없는 버전을 보고 그
학습 실행이 FINISHED인지 확인한 뒤** 판정을 호출한다(§9). 비동기 작업의 완료는 시간이 아니라 상태로
확인하고, 그 확인 주체를 실패 지점과 분리한다.

**여전히 없는 것.** CI는 문법 검사만 하고 **동작 시험이 없다.** 롤백은 미착수다. 매니페스트는 판정만
읽고, 학습·검증·내보내기는 아직 이 과제 전용 코드다.

lint는 의도적으로 좁게 잡았다 — 문법 오류·정의되지 않은 이름처럼 **실행하면 확실히 터지는 것만**
차단하고 스타일 규칙은 통과시킨다. 소규모 운영에서 스타일 게이트는 마찰만 키운다는 판단.

### 5.2 ONNX 3단계 검증기

배포 전 게이트를 세 단계로 나눴다:

1. **구조 검증** — `onnx.checker.check_model`로 스펙 준수 확인 (ir_version·opset·producer 출력)
2. **동적 배치 검증** — 입력에 동적 batch 차원이 있는지 확인. 없으면 기본적으로 FAIL
   (§10.6에서 실제로 이 문제를 겪었기 때문에 게이트로 승격)
3. **더미 추론** — ONNX Runtime CPU로 랜덤 입력을 실제 추론, 출력이 유한값인지 검사

"구조 OK → 동적 배치 OK → 실제로 로드·실행됨 OK"의 3단 게이트로, Triton에 올리기 전에 깨질 모델을
거른다.

### 5.3 배포 워크플로 — 검증에서 READY 확인까지

수동 배포 절차를 그대로 코드화한 것이 배포 워크플로다:

1. 체크아웃 → 의존성 설치
2. 입력 ONNX 존재·크기 확인
3. ONNX 검증기 재사용 (§5.2)
4. **`config.pbtxt` 존재 확인** — 없으면 실패. Triton EXPLICIT 모드의 전제(§3.1)
5. 모델 저장소로 ONNX 복사
6. **Triton load API 호출** — 200이 아니면 실패
7. **READY 폴링** — 준비 상태를 주기적으로 확인, 시간 내 안 되면 실패
8. 배포된 모델 메타데이터 출력
9. 레지스트리 거버넌스 갱신 (§5.4)

4~7번이 핵심이다. 파일을 복사했다고 배포가 끝난 게 아니라, **모델이 실제로 서빙 가능 상태가 된 것을
확인해야** 성공으로 친다.

### 5.4 CI 끝단에서 거버넌스 정합성을 코드로 강제

배포 워크플로 마지막 단계가 레지스트리를 자동 갱신한다. 원칙은 **"한 시점에 한 모델당 deployed는
1개"** 이고, 4단계로 강제한다:

1. 기존 `status=deployed` 버전을 전부 `retired`로 전이 (+ `retired_at`, 노트 append)
2. ONNX 아티팩트를 업로드해 run 생성
3. 새 model version 생성 (해당 run에 연결)
4. 새 버전에 `deployed` + timestamp + CI 실행 출처를 태깅

효과는 "사람이 태깅을 잊었나"를 걱정할 필요가 없어진다는 것이다. 레지스트리 UI에서 한 모델의
라이프사이클이 **하나의 deployed → 여러 retired**로 자연스럽게 시각화되고, "지금 무엇이 떠 있나"가
태그 조회 한 번으로 답이 된다.

의도적 제약도 하나 뒀다 — **Registered Model 자체는 CI가 자동 생성하지 않는다.** 최초 등록은 포털이나
CLI라는 단일 경로로만 가능하게 해서, 출처·담당자·모델 타입 같은 필수 메타데이터가 누락된 채로
모델이 생기는 걸 막았다.

### 5.5 알려진 구조적 약점 — validator 이원화

ONNX 검증기의 정본은 공용 도구 저장소에 있다. 그런데 조직 저장소가 private이라 CI 잡 컨테이너에서
cross-repo clone이 안 된다. 결국 모델 저장소 쪽에 **인라인 사본**을 두게 됐고, 두 사본이 따로 노는
**코드 드리프트 위험**이 구조적으로 생겼다.

이건 §10의 "도구를 별도 저장소로 분리" 결정의 대가다. 재사용성을 얻는 대신 동기화 비용을 치르는
트레이드오프였고, 현재는 파일 상단에 "한시적 인라인 사본, 변경 시 양쪽 동기화" 주석으로만 방어하고
있다 — 즉 **사람이 지켜야 하는 규칙**이라 근본 해결이 아니다.

## 6. 관측 — Prometheus + Grafana

### 6.1 수집 범위와 그 한계

Prometheus가 15초 주기로 Triton 메트릭을 수집하고, 30일 보관한다. Grafana 데이터소스·대시보드는
프로비저닝 파일로 코드화해 컨테이너를 다시 띄워도 자동 복원되게 했다.

**정직하게 남길 한계와, 알림을 다르게 푼 방식:**

- Prometheus 알림 룰은 **0개**이고 Alertmanager를 붙이지 않았다. 대신 알림은
  **운영 콘솔 점검 → 알림 점검 워크플로(평일 2회) → Git 이슈 발행, 해소되면 자동으로 닫힘** 경로로
  구현했다. 폐쇄망 밖으로 나가지 않고, 이미 쓰는 도구라 담당자 지정·처리 이력이 함께 남는다는 것이
  선정 이유다. 걸리는 항목이 있으면 워크플로 실행 자체를 실패로 끝내 목록에서 바로 보이게 했다.
- `node-exporter` / `cadvisor`가 없다 → **호스트·컨테이너 시스템 메트릭은 수집되지 않는다.**
  수집되는 건 Triton이 스스로 내보내는 메트릭뿐이다.

즉 관측 성숙도는 "메트릭 수집·시각화 + 점검 기반 이슈 알림"까지이고, 메트릭 임계값 기반 알림은 없다.

### 6.2 대시보드 설계

Triton 메트릭에 맞춘 7패널 대시보드를 구성했다: 초당 추론 요청 수, 연산 시간, 누적 추론 횟수,
GPU 사용률, GPU 메모리, GPU 전력, 대기 중 요청 수.

단순 health check가 아니라 **부하 → 자원 → 지연**을 한 화면에서 잇는 구성이다.

### 6.3 이건 부하 테스트가 아니다

관측 스택 검증은 **"메트릭이 실제로 흘러 대시보드에 뜨는가"** 를 확인한 것이지, 정식 성능 시험이
아니다. throughput·p99 지연·동시성 한계를 측정한 적이 없다.

표현 규칙: "부하 테스트 수행" ✗ → **"메트릭 수집 파이프라인 구축·검증"** ○.

## 7. 학습 환경

학습은 GPU 서버의 PyTorch 컨테이너에서 돌린다. 학습 스크립트가 실행되면 MLflow에 파라미터·메트릭·
모델이 자동으로 기록·등록되도록 클라이언트를 연결했다.

코드 경로는 의도적으로 **학습 로깅과 거버넌스 태깅을 분리**했다. 학습 스크립트는 실험 기록만 하고,
거버넌스 스크립트가 레지스트리 태그를 다룬다 — 책임이 다르기 때문이다.

학습은 주 1회 스케줄과 입력 분포 감시(§8)가 자동으로 시작한다. 사람이 직접 시작하는 경로도 남아 있다. 다만 **학습 데이터가 갱신되는 자리가 없다** — 같은 데이터·같은 시드로 다시 도는 재학습이라 재학습의 실질 효용은 아직 없고, 고리를 이은 것 자체가 현 단계의 성과다(§12).

## 8. 입력 분포 관측 — Evidently PoC와 콘솔 범위 감시

경로가 둘이다.

**Evidently PoC.** 입력 분포 변화를 관측하는 PoC를 붙였다. reference(기준 분포)는 실제 학습 데이터의
메타데이터에서 추출한 실측값이고, current(현재 분포)는 초기에 합성 데이터였다가 실제 추론 입력을
적재하는 구조로 전환했다. 스냅샷 생성은 스케줄되어 있지 않다. 이 경로는 여전히 "관측 파이프라인의
형태를 갖춘 PoC"다.

**콘솔 범위 감시 → 재학습.** 운영 콘솔(§9)이 콘솔 추론 경로를 거친 입력을 기록하고, 습도·온도·풍속
세 항목이 **학습 범위를 벗어났는지** 판정한다. 이탈이면 조건 5종(범위 이탈 · 표본 수 · 최근 학습
경과 일수 · 미실행 중 · 토큰)을 확인하고 학습을 호출한다. 2026-09-14에 임계값을 낮춘 시연(표본 5건·간격 1일)으로 이 경로가 동작해 한
버전을 만들었다 — 정본 설정(50건·3일)에서 자연 발화한 적은 없다.

정확히 적어야 할 한계: 추론 트래픽 자체가 스모크 수준이라 기록된 표본이 17건이다. 통계적 드리프트
판정이라기보다 **학습 범위 이탈 검사**에 가깝고, 표본이 모자란다는 사실을 먼저 말해야 한다.
"드리프트 기반 자동 재학습이 운영 중"이라고 말하면 과장이다.

## 9. 운영 UI — Streamlit 포털에서 운영 콘솔로

**Streamlit 포털(1세대).** MLflow·Triton·Grafana·Evidently를 각각 따로 열어보는 대신 한 화면에서
다루는 포털을 만들었다. 모델 업로드(검증 → Triton load → 레지스트리 등록), 모델 리스트·버전 비교,
서빙 모니터링(health + 메트릭 + Grafana 임베드), 거버넌스 트렌드, 추론 테스트로 구성했고,
설계 의도는 **거버넌스 스키마를 UI로 강제**하는 것이었다 — 업로드 경로를 포털로 단일화하면
필수 메타데이터 누락이 구조적으로 막힌다(§5.4).

**운영 콘솔(2세대, 2026-08-28~).** 자동화가 들어오면서 화면이 아니라 **자동화 주체**가 필요해졌다.
서버는 Python 표준 `http.server`가 JSON만 돌려주고, 화면은 Vue 2.7 + Element UI를 빌드 없이
vendor 파일째 저장소에 둔다 — 폐쇄망에 패키지 저장소를 들이지 않기 위한 선택이다. 메뉴는 10개,
"기능 하나에 메뉴 하나"다. 콘솔이 상시로 하는 일:

- **autogate** — 판정 없는 버전을 보고, 그 학습 실행이 FINISHED인지 확인한 뒤 판정을 호출한다.
  실행기 잡 수명보다 학습이 길어 워크플로가 학습을 끝까지 지켜보지 못하는 구멍을 시간 짐작 없이 메운다.
- **retrain** — 입력 분포 범위 이탈 시 학습을 호출한다(§8).
- **recover** — 60초마다 서빙 실체를 점검해 자동 유지로 지정된 모델이 내려가 있으면 다시 싣는다.
  재부팅 후 10개 전량 복구를 확인했다.
- **reconcile** — 등록부(선언) ↔ 실행기·추론 서버(실측)를 대조해 어긋난 곳을 조치 대상으로 올린다.
- **관리 항목 등록부** — SQLite. 자격증명은 값이 아니라 참조 키만 받고, 값처럼 보이는 문자열은 거부한다.
  모델 정보는 따로 만들지 않고 레지스트리를 정본으로 참조한다("레지스트리는 하나").

한계: 콘솔에 쓰기 동작이 있지만 로그인이 없다. 포털과 콘솔이 병행 가동 중이며 포털 폐기 시점은
정하지 않았다.

## 10. 의사결정 이력 — 왜 이 도구였나

모든 선택의 공통 상위 제약은 **자체호스팅 강제**(폐쇄망·데이터 주권 방침, 소규모 팀, 예산 제약)다.
거기서 나머지가 따라 나온다.

### 10.1 왜 Triton (vs TorchServe / TF Serving / KServe / BentoML)

핵심 기준은 **멀티 프레임워크**였다. 이 조직은 모델을 직접 개발하지 않고 외부에서 받아 서빙하는
패턴이라, **어떤 프레임워크로 올지 모르는 모델**을 한 서버로 받아내야 한다. 그래서
프레임워크 종속 서버는 처음부터 탈락했다 — TorchServe는 PyTorch 전용, TF Serving은 TensorFlow 전용.

KServe는 Kubernetes 의존이라 K8s 클러스터가 없는 단일 GPU 서버 환경에서 운영 ROI가 맞지 않았다
(로드맵에는 '향후'로 남겼다). BentoML은 패키징은 좋으나 GPU 메트릭 풍부함에서 Triton에 못 미쳤다.

Triton을 고른 부수 이유는 GPU 메트릭이 풍부해 Prometheus와 궁합이 좋고, 컨테이너 하나로 배포되며,
폐쇄망 친화적이라는 점이었다.

### 10.2 왜 MLflow (vs W&B / Neptune / ClearML)

**자체호스팅 가능(OSS, Apache-2.0)** 이 가장 큰 이유였다. W&B·Neptune은 SaaS가 기본이라 폐쇄망·예산
제약과 정면 충돌한다. 부수적으로 Tracking + Registry + Artifact를 한 도구로 끝낼 수 있고,
PyTorch/ONNX/scikit-learn 플레이버를 모두 지원한다.

같은 맥락에서 아티팩트 스토리지로 검토했던 MinIO는 **AGPL 라이선스 리스크** 때문에 스택에서 제거하고,
MLflow의 아티팩트 프록시 모드로 기능을 흡수했다(§4.2). 컴포넌트를 하나 줄이면서 라이선스 문제도
같이 해결한 결정이다.

### 10.3 왜 Gitea (vs GitHub / GitLab CE / Forgejo)

GitHub는 자체호스팅이 아니라 폐쇄망 정책상 원천 배제. GitLab CE는 자원 사용량이 커서 같은 서버에서
ML 워크로드와 공존시키기 부담스러웠다. Forgejo는 Gitea fork로 거의 동등하나 당시 커뮤니티·안정성
기준으로 Gitea를 택했다.

결정적 이점은 **Gitea Actions가 GitHub Actions YAML 문법과 호환**된다는 것이다. 학습 곡선이 낮고,
나중에 GitHub로 이관해도 워크플로를 거의 재작성하지 않아도 된다 — 제약 하에서 **출구 전략**까지
확보한 선택.

### 10.4 왜 Prometheus + Grafana (vs Datadog / New Relic)

자체호스팅 OSS가 의무라 SaaS APM은 검토 단계에서 원천 탈락했다. 추가 비교의 실익이 없었다.

### 10.5 왜 ONNX (vs TorchScript / TensorRT 직접)

**미래 옵션 보존**이 이유다. ONNX는 Triton의 표준 백엔드이면서, 동시에 ONNX Runtime·TensorRT·
OpenVINO 등 다른 런타임으로도 옮길 수 있어 벤더 락인을 피한다. TorchScript는 PyTorch 전용이라
외부 출처 모델까지 통일할 수 없고, TensorRT 직접 최적화는 하드웨어 종속이 강해 인수 모델마다 비용이
든다(ONNX → TensorRT 변환은 향후 옵션으로 남겨둠).

export opset은 17로 고정돼 있으나, **왜 17을 골랐는지의 근거 기록은 남아 있지 않다.**
모르는 건 모른다고 둔다.

### 10.6 왜 자체호스팅 (vs SageMaker / Vertex AI / Azure ML)

데이터 주권·폐쇄망 대응이라는 상위 방침과 예산 제약 때문에 사실상 강제된 선택이었다. 대가도 명확하다 —
유지보수 책임이 전부 내부에 있고(OS·드라이버 레벨 이슈까지), 고가용성 설계도 직접 신경 써야 하며,
SaaS의 운영 편의성을 포기한다.

다만 "클라우드를 모른다"가 아니라 **"비교한 뒤 제약상 안 골랐다"** 가 정확하다. 도입 결정 단계에서
프로세스별로 3사를 비교했고, 이후 실제로 hands-on 벤치마킹까지 수행했다(§12).

### 10.7 왜 단계적으로 구현했나

**"운영해보지 않은 컴포넌트는 추정만 남는다"** 는 원칙을 세웠다. 단일 운영자 규모에서 12개 프로세스를
동시에 벌리면 전부 반쯤 켜진 상태가 된다. 그래서 Level 0(기본 인프라)을 확실히 가동·검증한 뒤
L1(드리프트 감지)로, 그다음 L2(자동화)로 올라가는 순서를 택했다.

### 10.8 왜 도구를 별도 저장소로 분리했나

거버넌스·검증 도구를 모델 코드 저장소에서 떼어냈다. 다음 모델·다른 프로젝트에서 도구만 가져다 쓸 수
있게 하기 위해서다. 단점도 인지하고 있다 — 저장소가 늘고, 문서가 분산되며, 실제로 §5.5의 validator
이원화라는 대가를 치렀다.

## 11. 트러블슈팅 — 설계에 영향을 준 것들

### 11.1 직렬화 실패 → 모델 자산 자체를 바꾸다

초기 수령 모델에서 Keras Lambda 레이어가 marshal 직렬화에 실패해 로드가 안 됐다. 개별 우회 대신
**같은 구조의 다른 프레임워크 구현을 찾아 채택**하는 쪽으로 방향을 틀었다. 포맷 호환성 문제는
때로 변환기를 고치는 게 아니라 자산을 교체하는 게 맞다.

### 11.2 CI 체크아웃이 인증에서 hang

프라이빗 저장소 clone 시 표준 checkout 액션이 인증 토큰을 제대로 처리하지 못해 잡이 십 분 넘게
매달리다 타임아웃으로 죽었다. 액션을 버리고 **raw `git clone`으로 대체**해 수 초로 해결했다.
이 패턴이 이후 모든 워크플로의 체크아웃 표준이 됐다.

### 11.3 Alpine(musl) → Debian(glibc) 러너 전환

CI 러너의 잡 컨테이너가 Alpine 베이스였는데, **ONNX Runtime은 musl 휠을 제공하지 않아** 설치가
불가능했다. 이건 단순 설치 실패가 아니라 **미래를 막는 문제**였다 — ONNX 검증 자동화 자체가 성립할 수
없게 된다. 그래서 베이스 이미지를 glibc 계열로 전환했고, 이 전환이 §5.2·§5.3의 검증·배포 워크플로가
가능해진 전제 조건이 됐다.

### 11.4 ONNX에 정적 batch 차원이 박혀 Triton이 거부

외부 수령 ONNX를 등록하려 하자 "모델은 `[8, K]`를 기대하는데 config는 `[-1, K]`"라는 shape mismatch로
거부됐다.

원인은 흔한 함정이다. export 시 `dynamic_axes`를 명시했더라도, ONNX export가 **중간 텐서 shape를
`value_info`(모양 캐시)에 기록할 때 더미 입력의 batch 크기를 그대로 박아 넣는** 경우가 있다.
Triton의 shape inferencer는 그 캐시를 신뢰하기 때문에 충돌이 난다.

패치 스크립트를 만들어 해결했다:

1. ONNX 그래프 로드
2. 출력 텐서의 첫 차원을 정적 값에서 **symbolic 차원으로 강제**
3. **`value_info` 캐시 엔트리를 전부 삭제** — 박혀 있던 모양 정보 제거
4. `onnx.checker`로 무결성 확인
5. `shape_inference`로 재추론해 동적 차원으로 깨끗하게 풀리는지 검증
6. 저장

개별 엔트리를 하나씩 고치는 대신 **캐시를 비우고 재계산하게 두는 편이 안전·재현 가능**하다고 판단했고,
무작정 지운 게 아니라는 걸 보이기 위해 checker + 재추론으로 이중 확인했다. 이 경험이 §5.2 검증기의
2단계(동적 배치 강제)로 승격됐다.

### 11.5 패치가 수치를 망가뜨리지 않았는지 독립 검증

패치된 ONNX를 Triton에 올리기 전에, **서빙 인프라와 분리해서** CPU ONNX Runtime으로 직접 돌렸다.
좌표 36.9만 점에 대해 추론한 뒤(내부적으로는 약 68.9만 회 호출) 결과 물리량 범위가 원본 보고값과
일치하는지 확인했다. 일종의 회귀 검증이다.

배포 파이프라인을 신뢰하기 전에 **ground truth를 따로 확보**하는 절차를 둔 것이 요점이다.

## 12. 성숙도 진단 — Google MLOps Maturity Model

### 12.1 기준 프레임

- **Level 0 — Manual process**: 매 단계를 사람이 직접 트리거. 스크립트는 있어도 단계 간 자동 연결이 없음.
- **Level 1 — ML Pipeline Automation + CT**: 학습 파이프라인이 자동화되고, 데이터·드리프트 신호 기반
  **지속적 재학습(Continuous Training)** 이 돎.
- **Level 2 — CI/CD Pipeline Automation**: 파이프라인 코드 자체가 CI/CD로 빌드·테스트·배포되고
  구성요소가 패키지화되어 재사용됨.

### 12.2 12개 프로세스 매핑

Level 2 정의에서 출발해 이 환경에 필요한 프로세스를 12개로 정리하고, 각각에 도구를 매핑했다.

| # | 프로세스 | 도구 | 상태 |
|---|---|---|---|
| 1 | Tracking Server | MLflow | 구현 |
| 2 | Model Registry | MLflow Registry (태그 기반 거버넌스) | 구현 |
| 3 | Model Repository | MLflow 아티팩트 프록시 | 구현 |
| 4 | Git / 배포 설정 | Gitea | 구현 |
| 5 | GitOps 배포 | ArgoCD | 선정 · 미도입 |
| 6 | 서빙 컨트롤러 | KServe | 선정 · 미도입 |
| 7 | Inference Server | Triton | 구현 |

### 12.3 판정 — Level 1 도달, 단 경계를 분명히

2026년 6월 자체 진단은 **L0~1 사이, L1 미달**이었다. L1의 핵심인 CT(자동 재학습 트리거)가 없었고,
§4.5의 갭이 그 진단을 그대로 보여줬다 — 재학습은 있었는데 배포로 이어지는 자동 연결이 없었다.

2026-09-12에 학습 → 판정 → 변환 → 배포 → 서빙이 사람 개입 없이 한 바퀴 돌았고(이후 반복),
입력 분포 이탈 → 재학습 호출 경로는 09-14에 임계값을 낮춘 시연(표본 5건·간격 1일)으로 동작을 확인했다 — 정본 설정(50건·3일)에서 자연 발화한 적은 없다. 스케줄 기동부터 배포까지 사람 손 없이 간 완주는 2회(09-12 v10, 09-19 v13)다. 근거는 도구 보유가 아니라 실행 이력이다.

| L1 정의 요건 | 충족 근거 |
|---|---|
| 학습 파이프라인 자동화 | 학습 워크플로 주간 실행 — 데이터 검증 → 학습 위임 → 버전 등록 |
| 모델 검증(승격 게이트) | 판정 워크플로 + 매니페스트 임계값. 미달 버전 2건 기각 |
| 배포 자동 연결 | 판정 통과 → 변환 → 체크섬 대조 배포, 무인 완주 약 37분 |
| CT 트리거 | 콘솔 범위 감시 → 학습 호출 — 임계값 낮춘 시연 1회로 경로 확인(운영 조건 자연 발화 없음) |
| 오케스트레이션 | Gitea Actions 스케줄 + 콘솔 상시 루프(autogate · recover · reconcile) |
| 모니터링 → 트리거 | 이상 항목 → Git 이슈 / 범위 이탈 → 재학습 |

**같이 말해야 하는 미달 영역.** 학습 데이터가 갱신되는 자리가 없어 같은 데이터로 도는 재학습이며,
재학습의 실질 효용은 아직 없다. CI는 문법 검사만 하고 동작 시험이 없다. 플랫폼화는 판정까지만이고
학습·검증·내보내기는 과제 전용이다. 롤백이 없다. 데이터 반입 경로가 없다.
Level 2(파이프라인 코드 자체의 CI/CD)는 범위 밖으로 확정했다.

"Level 1 도달"과 이 미달 목록은 한 호흡으로 말해야 정확하다.

### 12.4 미완을 어떻게 다룰 것인가

미구현 항목을 숨기지 않고 **로드맵상의 다음 단계로 명시**하는 쪽을 택했다. "운영해보지 않은
컴포넌트는 추정만 남는다"(§10.7)는 원칙과 짝을 이룬다 — 안 켜본 것을 켰다고 말하지 않는 대신,
무엇이 왜 안 켜졌는지를 정확히 적는다.

## 13. 클라우드 매니지드 플랫폼과의 비교

### 13.1 비교 방식과 그 경계

도입 결정 단계에서는 문서 기반 비교였다. 이후 실제로 **Vertex AI와 Azure ML은 계정 개설 → 모델 등록 →
클린업까지 직접 사용(hands-on)** 했고, **SageMaker는 문서 기반**으로만 정리했다. 이 구분은 중요하다.

범위도 명확히 해둔다: 소형 ONNX 모델 · 무료 티어 · 비용 $0 범위의 **기능 탐색**이지, 프로덕션 운영이나
실제 이관이 아니다.

### 13.2 한 사이클(등록 → 리스트 → 배포 → 모니터링 → 추론 → 거버넌스) 비교

| 단계 | Vertex AI | Azure ML | SageMaker (docs) | 온프레 스택 |
|---|---|---|---|---|
| 등록 | 컨테이너 URI 명시 | 3가지 소스 | Package Group + 승인 상태 | 파일 업로드 → 스키마 자동 검증 |
| 배포 | 엔드포인트 명시 생성 | 4종 유형 | 4종 유형 | 파일 마운트 + load API → 즉시 READY |
| 모니터링 | 입력 드리프트 | 5축 | 4축 | Grafana 임베드 + 입력 드리프트 |
| 거버넌스 | 라벨 단일 | 태그 + 속성 + 설명 | 승인 상태 | 태그 스키마 다필드 + 트렌드 뷰 |

### 13.3 직접 써보고서야 알게 된 것

- **Vertex와 Azure 둘 다 ONNX를 네이티브 '유형'으로 두지 않는다.** Vertex는 커스텀 컨테이너 URI를
  명시해야 했고(결국 Triton 컨테이너를 지정했다), Azure는 형식이 CUSTOM으로 잡힌다. ONNX를 자동
  인식하는 Triton이 이 지점에선 더 단순하다.
- **3사 모두 "배포 = 엔드포인트를 명시적으로 생성"** 하는 단계가 있다. 온프레 Triton은 파일 배치 +
  load 호출로 즉시 READY라 이 단계가 절감된다.
- Azure는 **책임 있는 AI**(공정성·설명가능성·오류 분석) 탭이 내장이고, SageMaker는 **모델 승인
  워크플로**(Pending/Approved/Rejected)가 있다. 둘 다 온프레 스택에 없는 기능이다.

### 13.4 온프레 스택의 강점과 약점

**강점**: 거버넌스 태그 다필드 노출, 배포 즉시 READY, 인터랙티브 추론 위젯, 거버넌스 트렌드 뷰
(3사 모두 없음), 온프레 비용 구조.

**약점(도입 후보)**: 모델 간 Compare, 아티팩트 파일트리 뷰, Pipeline DAG UI, 확장 드리프트 축,
계보(lineage) 시각화, 승인 워크플로 UI. 이 중 Compare·아티팩트 트리·라이프사이클 전환 버튼은
이후 포털 개편에서 실제로 구현했다.

**도메인상 불필요**: Feature Store, 사전훈련 모델 카탈로그, 대량 batch inference,
컴퓨트 인스턴스 관리(온프레 GPU는 정액).

## 14. 정량 결과 — 측정 조건과 함께

원칙: **모든 수치는 측정 조건을 동반한다.** 측정하지 않은 건 "측정 안 함"으로 적고 추정치를 성과로
쓰지 않는다.

### 14.1 모델 성능 (도시냉각 3D U-Net)

**지표 값은 이 문서에 적지 않는다.** 온도 오차·적합도 수치는 국가과제 산출물이라 공개 문서에
옮기지 않고, 여기서는 *어떻게 측정했고 무엇을 신뢰할 수 있는가*만 남긴다 — 이 문서가 파는 것은
숫자가 아니라 측정 규율이다.

- 절대 오차(MAE)·RMSE·결정계수(R²)를 **Test split 기준**으로 기록하며, 학습 컨테이너가 매 run
  마다 MLflow 에 자동 적재한다. 승격 판정(§7)이 읽는 값이 바로 이것이다.
- 1·2차는 로컬 GPU 초기 실험이라 일부 지표와 분할 조건이 보존되지 않았다. **3차(GPU 서버
  재현)가 가장 방어 가능한 측정**이고, 인용할 일이 있으면 그것만 쓴다.
- 이 지표는 **학습 메트릭**이다. §4.5의 갭 때문에 현재 서빙 중인 바이너리의 성능과 1:1로
  일치한다고 단정하면 안 된다 — 오차 수준을 말해야 할 때 "1℃ 미만 수준의 대리모델" 처럼
  정성으로 내리는 이유다.

### 14.2 추론 응답 시간

| 대상 | 값 | 조건 |
|---|---|---|
| U-Net 추론 | **폐기** | 입력 크기·배치 조건이 영구 미상(WSL2 시절 측정) → 인용하지 않는다 |
| PINN 100점 추론 | **22~32ms** | 단일 요청, GPU, FP32 — 조건이 완전한 신뢰 수치 |
| PINN 36.9만 점 전체 | **약 24.5초** | 단일 프로세스, **CPU** ONNX Runtime |
| 같은 작업을 GPU 서빙으로 | **측정 안 함** | 더 빠를 것으로 추정하나 검증하지 않음 — 성과로 쓰지 않는다 |

### 14.3 CFD 대비 속도 (단서 필수)

협업 대학 측 측정에 따르면 기존 CFD 시뮬레이션은 **수십 분** 규모다(정확한 시간은 미확정).
AI 대리모델 추론은 그보다 몇 자리수 빠르다 — 단 **비교의 분자로 쓸 수 있는 신뢰 수치는
§14.2의 PINN 22~32ms 뿐**이고, U-Net 쪽 응답시간은 조건 미상으로 폐기했다.

그리고 **동등 비교가 아니다.** CFD는 완전한 물리 해석 결과이고 AI는 근사 대리모델(surrogate)이다.
출력의 성격이 다르므로 속도만 1:1로 비교하면 과장이 된다. "근사가 얼마나 정확한가"는 §14.1의
학습 지표가 답하는 몫이고, 그 지표는 §4.5의 갭을 달고 있다.

### 14.4 CI 실행 시간

- **과거**: 인증 hang 으로 십 분 넘게 매달리다 타임아웃(§11.2)
- **현재**: 수 초

단, **동일 작업의 순수 가속이 아니다.** 지금 빠른 이유는 lint + `py_compile`만 도는 캐시된
상태이기 때문이고, 첫 회 이미지 pull 은 별도로 수 분이 든다. 이 비교는 "hang 상태 해소 전후"다.
(정확한 초·분 값은 사내 실측이라 이 문서에 옮기지 않는다.)

### 14.5 측정하지 않은 것

정식 부하 테스트를 하지 않았다. throughput·p99 지연·동시성 한계는 측정 대상이 아니었다.
관측 스택에서 확인한 건 "메트릭이 실제로 흘러 대시보드에 반영되는가"까지다(§6.3).

## 15. 알려진 한계와 다음 단계

정직하게 나열하면:

| 항목 | 현 상태 | 다음 단계 |
|---|---|---|
| 학습 데이터 갱신 경로 | 없음 — 같은 데이터·같은 시드 재학습이라 CT의 실질 효용이 아직 없음 | 데이터 반입 경로 + 재학습 데이터셋 갱신 |
| 레지스트리 ↔ 실서빙 갭 | 해소 — 배포 정본 레지스트리 이전 + 해시 대조(§4.5) | 롤백(자동 배포와 짝이 되는 기능) 착수 |
| validator 이원화 | 인라인 사본 수동 동기화(§5.5) | 저장소 가시성 정책 해결 또는 패키지 배포 |
| 알림 | 점검 기반 Git 이슈 알림은 있으나 메트릭 임계값 룰은 0개 | 임계값 기반 알림 |
| CI 동작 시험 | 없음 — 문법 검사만 | 판정·계약 검증 스크립트 단위 시험부터 |
| 시스템 메트릭 | node/container exporter 없음 | exporter 추가 |
| 입력 분포 감시 | 표본 17건 — 추론 트래픽이 스모크 수준 | 실입력 축적 후 통계적 판정 기준 수립 |
| 동적 배치 | 안전값, 미튜닝 | 부하 측정 기반 튜닝 |
| ONNX opset 선택 근거 | 기록 없음 | 재확인 |

이 표가 이 문서에서 가장 중요한 부분일 수 있다. **무엇을 안 했는지 정확히 아는 것**이
성숙도 진단(§12)의 실질이고, 안 켜본 것을 켰다고 말하지 않는 것이 이 문서 전체의 규율이다.
